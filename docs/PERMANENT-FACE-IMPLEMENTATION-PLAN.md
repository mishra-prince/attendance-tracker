# Permanent face verification implementation

24 October 2026. Extend the existing Threshold APK, central User/refresh-session auth, ClassSession attendance, scoped staff rosters and RFID reader evidence. Preserve the APK identity/signature and existing student data. Do not promote a local demo template or accept client faceMatch/liveness booleans as institutional verification.

## Current gaps

The native demo has CameraX/ML Kit action guidance and real OpenCV SFace embeddings, but stores a PIN-approved local template unrelated to student accounts. The institutional enrollment API currently records staff observations only, without a captured face reference, and does not consistently scope staff to their students. The permanent flow needs its own authorized camera capture, encrypted server-held reference and server verification. Old metadata remains readable but is not a usable face enrollment.

## Implementation

1. Add an encrypted face reference to BiometricEnrollment, with an explicit model version and capture timestamp. Existing metadata stays template-free until supervised capture. Only scoped authorized staff may enroll/recover/revoke a student's identity. Consent and in-person ID confirmation accompany enrollment. Audit every mutation atomically; never log face images/templates/passwords.
2. Add expiring, single-use server FaceChallenge records bound to the requesting login, student, enrollment version, operation and (for attendance) actual class session. Server selects unpredictable actions. Reject replay, changed identity/version, wrong staff/student scope, out-of-order/expired submissions and unsupported evidence. Record verification outcomes separately; failures are technical/review states, never accusations.
3. Capture a bounded sequence of small JPEG camera frames in a permanent native activity. Use the existing ML Kit guidance/preparation/start UX and randomized visible actions. Release camera on pause/cancel. Return bounded images through a one-use, expiring RAM transfer and the authenticated main flow; no external activity may launch the capture. Never return institutional templates to students or treat a demo result as proof.
4. Recompute face recognition and action evidence on the server from submitted frames using pinned OpenCV YuNet/SFace and MediaPipe Face Landmarker models. Do not trust client-provided vectors, action labels or success flags. Bound frame count, dimensions, payload, CPU work, queue and deadlines; discard raw frames after analysis. Load the vision worker only when needed and keep concurrency bounded for the free host. Document this as basic active liveness, pending presentation-attack/injection and load validation.
5. Integrate main staff enrollment, student face verification/due-check screens, admin settings, scoped teacher/admin status/history and enrollment revocation/recovery. Keep randomized foreground reminders separate from guaranteed background notifications; camera always requires a visible session. Attendance requires independent server classroom evidence. The owner explicitly selected mandatory face verification. Default to requiring entry + random face checks before automatic RFID credit; this policy is snapshotted at first entry so ongoing classes are unaffected.
6. Extend schema additively with migrations/RLS, use the existing single percentage service and transaction audit. Verify migration/auth/scope/replay/enrollment/expiry/identity/action/attendance integration, real model inference on public test fixtures and native lifecycle/build/signature. Stage deployment only after the code/build is reviewable, preserve existing hosting secrets and do not replace the live service with an unavailable verifier.

## Constraints

RFID/ESP evidence cannot establish who holds a card, and unsigned A17C demo beacons cannot establish secure room presence. Do not enable demo BLE signals for production credit. Keep existing authenticated BLE workflows distinct. No background camera, personal-phone lock, corridor containment, iPhone support, robust PAD, battery measurement or 95% reliability claim without evidence. Missing checks must support an audited staff fallback/correction rather than silently assigning absence. Do not run the destructive demo seed against Supabase.
